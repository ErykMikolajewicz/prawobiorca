# AI Module (LLM Service)

The module generates formal letters and student applications in DOCX format from case details, student data and related legal provisions.

## 1. Architecture and Integration

- **Endpoints** (`src/core_service/framework/api/endpoints/cases.py`):
  - `POST /api/cases/{caseId}/applications` accepts `NewApplication` (`src/core_service/application/dtos/applications.py`), saves an application with the `IN_PROGRESS` status, schedules background generation and returns `202` with the application ID. It returns `404` for a missing or unpublished template, and `422` with a list of field names for invalid field values.
  - `GET /api/cases/{caseId}/applications` returns the case's applications (`ApplicationRepresentation`) with their generation status.
  - `GET /api/cases/{caseId}/applications/{applicationId}/download-url` returns a presigned URL for the DOCX file. It returns `409` unless the application's status is `GENERATED`.
  - `DELETE /api/cases/{caseId}/applications/{applicationId}` deletes the application and its file.
- **Application template:** `NewApplication` contains the `templateId` of a published template managed by the administrator, a situation description (`description`) and template field values (`fieldValues`), validated by `ApplicationTemplate.validate_field_values` (`src/core_service/domain/entities/application_template.py`). The template provides AI instructions (`instructions`), field definitions and a DOCX file in object storage. The application stores `template_id` (`NULL` after template deletion) and a copy of the template name (`template_name`).
- **Application name:** the `name` field in `ApplicationRepresentation` is generated by the LLM from the situation description (prompt `prompts/application_name.md`) and saved together with the `GENERATED` status. Until then, it is `null` and the frontend displays the template name instead.
- **Generation status:** `ApplicationGenerationStatus` (`src/core_service/domain/value_objects/applications.py`): `IN_PROGRESS`, `GENERATED`, `FAILED`.
- **Use cases** (`src/core_service/application/use_cases/applications.py`): `AddApplication` (saves the application and schedules the task), `GenerateApplication` (executed by the worker), `FailApplicationGeneration`, `ListApplications`, `GetApplicationDownloadUrl`, `DeleteApplication`.
- **Background task:** `generate_application` (`src/core_service/framework/workers/applications.py`), scheduled by `PostgresApplicationGenerationScheduler` (`src/core_service/infrastructure/tasks/applications.py`) in the same transaction that saves the application.
- **Ports:** `src/core_service/application/ports/applications.py` (`ApplicationWriter`, `ApplicationRenderer`).
- **Adapters:**
  - `LlmApplicationWriter` (`src/core_service/infrastructure/ai_services/application_writer.py`) implements the `ApplicationWriter` port, renders a Jinja2 prompt (`src/core_service/infrastructure/ai_services/prompts/application.md`) with template instructions and application data, and generates content through `LlmChat`. A separate call (`write_name`, prompt `src/core_service/infrastructure/ai_services/prompts/application_name.md`) generates the application name.
  - `LlmChat` (`src/core_service/infrastructure/ai_services/llm_chat.py`) is a client for an OpenAI-compatible chat API: Vertex AI Model-as-a-Service on GCP, or the OVMS `llm` container on-premise and locally (host port 8083 / cluster port 8080).
  - `DocxApplicationRenderer` (`src/core_service/infrastructure/docx/docx_renderer.py`) renders a DOCX template fetched from object storage in a `SandboxedEnvironment`, using field values, `current_date` and `paragraphs` (constants `CURRENT_DATE_TEMPLATE_VARIABLE` and `CONTENT_TEMPLATE_VARIABLE`), and returns it as `bytes`.
  - `SqlaApplicationsRepository` (`src/core_service/infrastructure/relational_db/repositories/applications.py`) uses the `applications` table. An application belongs to a case and is deleted with it through cascading deletion.
  - `S3ApplicationsStorage` (`src/core_service/infrastructure/object_storage/repository.py`) stores DOCX files in object storage under `applications/{id}`.
- **Configuration:** `LLM_SERVICE_*` environment variables (`src/core_service/shared/settings/ai_services.py`); only `LLM_SERVICE_URL` is required (the API base URL including `/v1`). On GCP, `LLM_SERVICE_USE_GOOGLE_AUTH=true` enables authentication with an OAuth token from Workload Identity (`src/core_service/infrastructure/ai_services/openai_client/google_auth.py`).

## 2. Application Templates

The administrator manages templates, and logged-in users see only published ones. Use cases receive `Caller` and check access through policies in `src/core_service/domain/services/application_template_access.py` (`check_can_manage_application_templates`, `check_can_read_published_application_templates`).

- **Endpoints** (`src/core_service/framework/api/endpoints/application_templates.py`):
  - `GET /api/application-templates/published` returns published templates (`PublishedApplicationTemplate`) with descriptions and field definitions, without AI instructions. It is available to logged-in users.
  - `GET /api/application-templates/published/search` searches published templates by name, optionally assisted by their descriptions; see [Template Descriptions](#5-template-descriptions).
  - `GET /api/application-templates` and `GET /api/application-templates/{templateId}` return templates (`ApplicationTemplateRepresentation`) regardless of status.
  - `POST /api/application-templates` accepts a template name, saves the template with default instructions and returns a presigned POST for uploading the DOCX file.
  - `POST /api/application-templates/{templateId}/confirm-upload` fetches the file from object storage, reads its variables, creates default fields from them and changes the status to `DRAFT`. The file is fetched and inspected outside the transaction. `ApplicationTemplate.confirm_upload` changes the status while the template is locked in a transaction (`SELECT ... FOR UPDATE`), so only a template with the `NOT_UPLOADED` status can proceed. The endpoint returns `409` if the upload has already been confirmed (including concurrently) or the file is missing from object storage, and `422` for an invalid DOCX template.
  - `PUT /api/application-templates/{templateId}` saves the name, instructions, description and field configuration (`ApplicationTemplateDetailsData`). Only the `DRAFT` status is accepted (otherwise `409`); invalid field configuration or a suborganization without an organization returns `422`.
  - `POST /api/application-templates/{templateId}/publish` publishes a `DRAFT` template with non-empty instructions (`ApplicationTemplate.publish`, otherwise `409`).
  - `POST /api/application-templates/{templateId}/unpublish` returns a published template to `DRAFT` (`409` otherwise).
  - `GET /api/application-templates/{templateId}/download-url` returns a presigned URL for the DOCX file (`409` if the file has not been uploaded). The frontend uses it to download and preview the template.
  - `POST /api/application-templates/{templateId}/description-generation` schedules description generation; see [Template Descriptions](#5-template-descriptions).
  - `DELETE /api/application-templates/{templateId}` deletes the template and its file. Generated applications are kept, with `template_id` set to `NULL`.
- **Status:** `ApplicationTemplateStatus` (`src/core_service/domain/value_objects/application_templates.py`): `NOT_UPLOADED` → `DRAFT` ⇄ `PUBLISHED`. Transitions and template rules are methods of the `ApplicationTemplate` entity (`src/core_service/domain/entities/application_template.py`).
- **DOCX file:** a Jinja2 template for docxtpl. It must contain the `paragraphs` variable (content generated by the LLM); `current_date` is filled automatically. The heading, addressee, salutation, closing and signature belong to the template and are not generated by the LLM. Other variables become template fields (`ApplicationTemplate.confirm_upload`).
- **Fields** (`ApplicationTemplateField`): variable name, label, type (`TEXT`, `NUMBER`, `SELECT`, `DATE`), `required`, `passToAi`, and optional default value, `pattern` and `options`. Configuration rules (`ApplicationTemplate.update_details` and `ApplicationTemplateField.check_config`):
  - the field set must match the template variables, without duplicates,
  - `pattern` must be a valid regex and is allowed only for `TEXT`,
  - `options` are required for `SELECT` and forbidden for other types,
  - a default value must pass field validation.

  User-entered values are validated by `ApplicationTemplate.validate_field_values` (`ApplicationTemplateField.accepts` for an individual field): `NUMBER` must be finite, `SELECT` must match an option, `DATE` must use `dd.mm.yyyy`, and `TEXT` must fully match `pattern`.
- **AI instructions:** Markdown edited by the administrator. New templates receive default instructions from `src/core_service/infrastructure/ai_services/prompts/application_template_instructions.md`.
- **Use cases** (`src/core_service/application/use_cases/application_templates.py`): `ListApplicationTemplates`, `GetApplicationTemplate`, `ListPublishedApplicationTemplates`, `AddApplicationTemplate`, `ConfirmApplicationTemplateUpload`, `UpdateApplicationTemplate`, `PublishApplicationTemplate`, `UnpublishApplicationTemplate`, `DeleteApplicationTemplate`, `GetApplicationTemplateDownloadUrl`.
- **Ports:** `src/core_service/application/ports/application_templates.py` (`ApplicationTemplateInspector`, `ApplicationTemplateInstructionsProvider`).
- **Adapters:**
  - `DocxTemplateInspector` (`src/core_service/infrastructure/docx/template_inspector.py`) reads DOCX template variables in a `SandboxedEnvironment` and extracts text from paragraphs and table cells for description generation.
  - `PromptsApplicationTemplateInstructionsProvider` (`src/core_service/infrastructure/ai_services/application_template_instructions.py`) provides default AI instructions.
  - `SqlaApplicationTemplatesRepository` (`src/core_service/infrastructure/relational_db/repositories/application_templates.py`) uses the `application_templates` table.
  - `S3ApplicationTemplatesStorage` (`src/core_service/infrastructure/object_storage/repository.py`) stores DOCX files in object storage under `application_templates/{id}`.

## 3. Application Generation Pipeline

1. `core` saves the application with the `IN_PROGRESS` status and inserts a Taskiq task into the queue in the same transaction. Form data (`NewApplication`) is stored only in the task arguments, not with the application. The task row is deleted after execution.
2. The worker fetches the template (instructions, fields and DOCX file) and the provisions pinned to the case. If the template has been deleted, is no longer published, or field values fail `ApplicationTemplate.validate_field_values` against its current configuration, the application is marked as `FAILED`.
3. Jinja2 renders the prompt: template instructions followed by XML data blocks (`<dane_wniosku>` with fields marked `passToAi`, `<opis_sytuacji>`, `<podstawa_prawna>`).
4. The LLM generates the substantive justification, then a separate call generates a short application name.
5. docxtpl combines the generated text with the DOCX template to produce the document.
6. The name is saved, the file is stored in object storage, and the status changes to `GENERATED`. The frontend polls the application list while any application is `IN_PROGRESS` and downloads the finished file through a presigned URL.

Error handling:

- LLM unavailability (`ServiceUnavailable`) retries the task with an increasing delay (`SmartRetryMiddleware`, with the delay implemented through `locked_until` in `task_messages`). The application stays `IN_PROGRESS` between attempts and becomes `FAILED` only after the last attempt fails. The task identifies the last attempt from the `_retries` and `max_retries` labels (`is_last_attempt` in `infrastructure/tasks/connection.py`).
- Other errors set `FAILED` immediately, without retrying.
- Exceeding the delivery limit (`MAX_APPLICATION_GENERATION_DELIVERIES`) sets `FAILED` without another attempt.
- If the application or case is deleted during generation, the worker ends the task without saving the file.

## 4. Regulation Descriptions

The administrator can request an LLM-generated general description of a regulation (2–4 sentences explaining what and whom the document concerns and the main areas it regulates, without deadlines, amounts or unit numbers). The description supports vector search for a relevant legal act, so its vector is saved alongside it.

- **Generation status:** `DescriptionStatus` (`src/core_service/domain/value_objects/descriptions.py`, shared by regulations and templates): `NOT_REQUESTED`, `IN_PROGRESS`, `GENERATED`, `FAILED`, returned as `descriptionStatus` in `RegulationRepresentation`. Transitions are methods of the `Regulation` entity (`src/core_service/domain/entities/regulation.py`), shared with templates through `Describable` (`src/core_service/domain/entities/describable.py`).
- **Request on creation:** `POST /api/regulations` with `generateDescription: true` (administrator only, otherwise `403`) saves the regulation with description status `IN_PROGRESS`. After setting `PREPARED`, `PrepareRegulation` schedules description generation in the same transaction. The description uses the sections saved during preparation, without extracting the document again.
- **Regeneration:** `POST /api/regulations/{regulationId}/description-generation` (administrator only) sets `IN_PROGRESS` and schedules the task. It returns `409` if the regulation is not prepared or its description is already being generated.
- **Background task:** `generate_regulation_description` (`src/core_service/framework/workers/regulations.py`), use case `GenerateRegulationDescription`. The LLM input (`create_description_source`, `src/core_service/domain/services/regulation_description.py`) contains the document name, a table of contents built from section headings (chapters and editorial unit titles without their numbers, up to `MAX_DESCRIPTION_HEADINGS`), and the beginning of the text (up to `MAX_DESCRIPTION_BEGINNING_CHARS` characters). Prompt: `src/core_service/infrastructure/ai_services/prompts/regulation_description.md`.
- **Description vector:** the `regulations.description_vector` column is computed by the worker for an LLM-generated description, using `embedding-batch` on GCP. Manually changing the description (`PATCH /api/regulations/{regulationId}`, use case `UpdateRegulation`) recomputes its vector synchronously through `embedding`, outside the transaction, as with templates. If the service is unavailable, saving returns `503` and the regulation remains unchanged. Removing the description clears the vector.
- **Search by description:** `GET /api/regulations/search` (use case `SearchRegulations`) accepts a natural language query (`query`), minimum similarity (`threshold`) and the same filters as the regulation list (`scope`, `documentType`, `organizationId`, `suborganizationId`). `embedding` converts the query into a vector. The result is a list of `RegulationSearchResult` objects (regulation and `score`, the cosine similarity), sorted by descending similarity. Regulations without a description vector are excluded.
- **Error handling:** as with applications, `ServiceUnavailable` retries the task and sets `FAILED` only after the last attempt fails. Other errors and exceeding `MAX_REGULATION_DESCRIPTION_GENERATION_DELIVERIES` set `FAILED` immediately.
- **Frontend:** a “Wygeneruj opis przez AI” checkbox in the regulation upload dialog and a button with the same label in a prepared regulation's details (both administrator only). During generation, the description field is disabled and the regulation list is polled until completion. On the Main Screen, `RegulationsSearchForm` searches both public and user lists by description, supports a relevance threshold and alphabetical or relevance ordering, and shows similarity for each regulation. Search parameters are stored in the page URL.

## 5. Template Descriptions

The administrator can request an LLM-generated short description of an application template (1–3 sentences explaining what the applicant requests, whom the letter addresses and when to use it). The description and its vector help users find a matching template. The description is also displayed during template selection.

- **Generation status:** `DescriptionStatus` (`src/core_service/domain/value_objects/descriptions.py`): `NOT_REQUESTED`, `IN_PROGRESS`, `GENERATED`, `FAILED`, returned as `descriptionStatus` in `ApplicationTemplateRepresentation`. Transitions are methods of the `ApplicationTemplate` entity (`src/core_service/domain/entities/application_template.py`).
- **Request:** `POST /api/application-templates/{templateId}/description-generation` (use case `RegenerateApplicationTemplateDescription`, administrator only) sets `IN_PROGRESS` and schedules the task in the same transaction. It returns `202`, `404` for a missing template, and `409` if the template is not `DRAFT` or description generation is already in progress.
- **Background task:** `generate_application_template_description` (`src/core_service/framework/workers/applications.py`), use case `GenerateApplicationTemplateDescription`. The LLM input (`ApplicationTemplate.create_description_source`, `src/core_service/domain/entities/application_template.py`) contains the template name, AI instructions (up to `MAX_DESCRIPTION_INSTRUCTIONS_CHARS` characters), field labels and DOCX text fetched from object storage (up to `MAX_DESCRIPTION_CONTENT_CHARS` characters). Prompt: `src/core_service/infrastructure/ai_services/prompts/application_template_description.md`. It instructs the LLM to omit general editorial guidelines shared by the default instructions of all templates.
- **Ports and adapters:** `ApplicationTemplateDescriptionWriter` (`src/core_service/application/ports/application_templates.py`, adapter `src/core_service/infrastructure/ai_services/application_template_description_writer.py`) and `ApplicationTemplateDescriptionGenerationScheduler` (`src/core_service/application/ports/tasks.py`, adapter `PostgresApplicationTemplateDescriptionGenerationScheduler` in `src/core_service/infrastructure/tasks/application_templates.py`).
- **Description vector:** the `application_templates.description_vector` column is computed by the worker for an LLM-generated description. Manually changing the description (`PUT /api/application-templates/{templateId}`, use case `UpdateApplicationTemplate`) recomputes its vector synchronously through `embedding`, outside the transaction, so saving on GCP may wait for a cold start. If the service is unavailable, saving returns `503` and the template remains unchanged. Removing the description clears the vector.
- **Template search:** `GET /api/application-templates/published/search` (use case `SearchPublishedApplicationTemplates`, logged-in users) accepts a query (`query`), an AI-assisted search flag (`aiAssisted`) and an organization filter (`organizationId`, `suborganizationId`). It returns published templates (`PublishedApplicationTemplate`) in ranking order, without scores.
  - **Fuzzy name search** (default): `word_similarity` from `pg_trgm` on names with Polish diacritics removed (`unaccent`), with the `TEMPLATE_NAME_SIMILARITY_THRESHOLD` threshold, sorted by descending similarity.
  - **Hybrid search** (`aiAssisted` and a query containing a space after at least one word, checked by `is_semantic_search_query` in `src/core_service/domain/services/application_templates.py`): the whole query is embedded, and the score is `TEMPLATE_NAME_SCORE_WEIGHT · name similarity + (1 − TEMPLATE_NAME_SCORE_WEIGHT) · description cosine similarity`. A template without a description vector has cosine similarity 0. No threshold is applied; the best `HYBRID_TEMPLATE_SEARCH_LIMIT` results are returned.
- **Error handling:** as with regulation descriptions, `ServiceUnavailable` retries the task and sets `FAILED` only after the last attempt fails. Other errors and exceeding `MAX_APPLICATION_TEMPLATE_DESCRIPTION_GENERATION_DELIVERIES` set `FAILED` immediately.
- **Frontend:** the template editor (`ApplicationTemplateEditor`) has an “Opis szablonu” field and a “Wygeneruj opis przez AI” button, which first saves the draft. During generation, the form is disabled and the template page polls until completion. In the application form (`GeneratePdfForm`), the “Rodzaj wniosku” selector sends a query after a pause in typing (the default `el-select` debounce), shows a loading state while searching and displays templates in backend ranking order. If search fails, it shows an error and the full template list. The “Wyszukiwanie AI” switch enables hybrid search. Template descriptions appear in tooltips on the options.

## 6. Models

| Environment | Model | Notes |
| --- | --- | --- |
| **GCP** | `google/gemini-3.5-flash-lite` (Vertex AI) | Serverless, billed per token. The `eu` multi-region (`aiplatform.eu.rep.googleapis.com`) processes data only within the EU. Requires `roles/aiplatform.user` (`scripts/cloud/cloud_inith.sh`). |
| **On-premise** | `OpenVINO/Qwen3.6-35B-A3B-int4-ov` (OVMS, `qwen-3.6-35b`) | `deploy/local/llm.yaml`. Mixture of experts, about 3B active parameters. |
| **Local development** | `OpenVINO/Qwen3.5-9B-int4-ov` (OVMS, `qwen-3.5-9b`) | `apps/core/scripts/dev.py`, a lighter model for testing. |

Previously tested: `OpenVINO/Qwen2.5-7B-Instruct-int4-ov`, `OpenVINO/gemma-2b-it-int8-ov` (no `system` role, limited Polish corpus), `OpenVINO/gemma-4-E4B-it-int8-ov` (`Segmentation fault` in OVMS 2026.3), `google/gemma-4-26b-a4b-it-maas` and `OpenVINO/gemma-4-26b-a4b-it-int4-ov` (replaced by Gemini 3.5 Flash-Lite and Qwen 3.6 35B A3B for better results).
